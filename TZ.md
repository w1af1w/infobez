# Техническое задание
## Кейс № 2. Система контроля сессий

### 1. Цель работы
Улучшить существующий сайт регистрации и входа пользователей. Добавить авторизацию с помощью двух токенов, страницу профиля и возможность безопасно завершить сеанс работы.

### 2. Используемые технологии
- **JWT** — создание и проверка Access-токена.
- **Crypto** — создание случайного Refresh-токена и его хеша.

**Access-токен** подтверждает, что пользователь вошёл в систему. Он действует **15 минут**. **Refresh-токен** позволяет получить новый Access-токен без повторного ввода пароля. Общая сессия действует **не более 8 часов**, но завершается раньше, если пользователь **15 минут ничего не делает**.

Пример: пользователь вошёл в 12:00. В 12:15 Access-токен истекает, но при действующей сессии его можно обновить. В 20:00 потребуется войти снова, даже если пользователь был активен всё это время.

### 3. Функциональные требования

**3.1. Вход в систему**
- Сохранить существующую проверку логина и пароля.
- После успешного входа создать Access-токен на 15 минут и Refresh-токен.
- Передать Access-токен приложению, а Refresh-токен — в cookie.
- В базе данных создать запись сессии: пользователь, хеш Refresh-токена, время входа, последней активности и завершения сессии.

**3.2. Страница профиля**
- После входа открывать профиль с логином пользователя и кнопкой «Выйти».
- Перед выдачей данных профиля сервер проверяет Access-токен и состояние сессии в базе данных.
- Без действующей авторизации данные профиля не выдавать.
- При успешном обращении к защищённому ресурсу обновлять время последней активности.

**3.3. Обновление токенов**
- Когда Access-токен истёк, приложение может запросить новый с помощью Refresh-токена.
- Сервер проверяет, что сессия ещё действует.
- При обновлении выдавать **новый Access-токен и новый Refresh-токен**, а старый Refresh-токен делать недействительным. 
- Не продлевать общий срок сессии более 8 часов.
- Не обновлять токены после 15 минут бездействия, после выхода или окончания сессии.
- При обновлении Access-токена предыдущий Access-токен должен становиться недействительным. Для этого сервер хранит в базе данных текущую версию токена и проверяет её при каждом защищённом запросе. При обновлении версия меняется, поэтому старый Access-токен больше не принимается.

**3.4. Выход**
- При нажатии кнопки «Выйти» завершать сеанс пользователя и удалять данные, необходимые для повторного входа без пароля.
- После выхода запрещать доступ к данным профиля даже по ранее выданному Access-токену.
- Возвращать пользователя на страницу входа.

### 4. Требования к интерфейсу
- Оставить существующие страницы регистрации и входа.
- Добавить страницу профиля с логином и кнопкой «Выйти».
- При истечении Access-токена автоматически пытаться обновить его.
- Если сессия закончилась, показывать сообщение: «Сессия истекла. Войдите снова» и открывать страницу входа.
- Хранить Access-токен только во время работы приложения, не сохраняя его в браузере для дальнейшего использования.

### 5. Требования к безопасности
- Проверять подпись и срок действия JWT, а также наличие действующей сессии в SQLite.
- Refresh-токен создавать случайным; в базе хранить **только его хеш**, а не сам токен.
- Обеспечить безопасное хранение Refresh-токена в браузере, чтобы посторонние не могли получить к нему доступ.
- Защитить обновление токенов и выход из системы от выполнения посторонними сайтами без согласия пользователя.
- Хранить секрет JWT в переменных окружения, а не в исходном коде.
- Не выводить пароли и токены в журналы сервера.
- Сохранить существующее хеширование паролей Argon2id и ограничение попыток входа.
- Обеспечить работу сайта через HTTPS для защиты паролей и токенов при передаче между браузером и сервером.
- Хранить Refresh-токен в cookie.

### 6. Изменения в существующем проекте
- **`src/server.js`** — добавить создание и проверку токенов, маршруты профиля, обновления и выхода.
- **SQLite** — добавить таблицу `sessions` для хранения данных о сессиях.
- **`public/login.js`** — после успешного входа открывать профиль.
- **`public/profile.html` и `public/profile.js`** — создать страницу профиля и кнопку выхода.
- **`package.json`** — добавить библиотеку для JWT.
- **`.env`** — хранить секрет JWT; не загружать этот файл в Git.
- **`README.md`** — кратко описать запуск проекта и работу токенов.

## 7. Модель угроз, последствия и способы защиты

### 7.1. Угрозы, от которых предусмотрена защита

1. **Кража Access-токена.** Посторонний может получить доступ к аккаунту. Для защиты срок действия токена ограничивается 15 минутами, а сервер проверяет состояние сессии.
2. **Кража Refresh-токена.** Злоумышленник может использовать его для продления доступа к аккаунту. Для защиты токен безопасно хранится и заменяется новым при обновлении.
3. **Использование просроченного токена.** Пользователь или злоумышленник может попытаться войти с помощью старого токена. Сервер проверяет срок действия и отклоняет просроченные токены.
4. **Подделка Access-токена.** Злоумышленник может попытаться создать поддельный токен для входа в чужой аккаунт. Для защиты сервер проверяет его подлинность с помощью секретного ключа.
5. **Повторное использование старого Refresh-токена.** Злоумышленник может попытаться получить доступ с помощью ранее использованного токена. После обновления старый токен перестаёт действовать.
6. **Длительное бездействие пользователя.** Если пользователь оставил аккаунт открытым, им может воспользоваться посторонний. Для защиты сессия автоматически завершается после 15 минут бездействия.
7. **Доступ после выхода из аккаунта.** Посторонний может попытаться воспользоваться токенами завершённой сессии. При выходе сервер завершает сессию и запрещает дальнейшее использование её токенов.
8. **Выполнение действий через посторонний сайт.** Злоумышленник может попытаться выполнить действия от имени пользователя без его согласия. Для защиты сервер проверяет, что запросы поступают от самого приложения.

### 7.2. Угрозы, защита от которых выходит за рамки проекта

1. **Вирусы на компьютере пользователя.** Вредоносные программы могут украсть пароли и другие данные. Для защиты необходимо использовать антивирусное программное обеспечение.
2. **Фишинг.** Пользователь может ввести свои данные на поддельном сайте. Для предотвращения таких ситуаций требуются дополнительные средства защиты и внимательность пользователя.
3. **DDoS-атака.** Злоумышленники могут отправлять большое количество запросов, из-за чего сервер перестанет работать. Для защиты требуется специальное оборудование или дополнительные сервисы.
4. **Взлом сервера.** Злоумышленник может получить доступ к базе данных и изменить или украсть информацию. Для предотвращения этого необходима комплексная защита сервера.
5. **Физический доступ к серверу.** Посторонний человек может получить доступ к оборудованию и хранящимся данным. Для защиты необходимо ограничивать доступ к серверу.
6. **Взлом браузера пользователя.** Злоумышленник может получить доступ к открытому аккаунту. Для защиты необходимо обеспечивать безопасность браузера и компьютера пользователя.
